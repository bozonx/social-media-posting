# Package Readiness & Platform-Extensibility Plan

**Status:** delivered (rev. 2) — every phase below is implemented; see `docs/CHANGELOG.md`
**Created:** 2026-08-15
**Supersedes:** rev. 1 of the same document
**Goal:** превратить репозиторий в веб-стандартную библиотеку публикации в соцсети, у которой
единственная оставшаяся работа — добавление новых сетей: каждая сеть это изолированный
пакет, реализующий стабильный контракт, плюс прогон общего conformance-сьюта.

## Что изменилось относительно rev. 1

Rev. 1 исходила из того, что проект остаётся NestJS-приложением, у которого library mode —
второй режим запуска. Пересмотр принял четыре решения, которые меняют почти каждую фазу:

1. **Продукт — библиотека. HTTP — деплой-артефакт, а не продукт.** HTTP-шелл остаётся
   исключительно ради не-Node потребителей (Python/Go/PHP-бэкенды, self-host). Он не
   публикуется в npm, только Docker-образ и Workers-деплой.
2. **NestJS уходит из ядра целиком.** Не «инжектим логгер через Nest-токен» (как предлагала
   rev. 1, п. 1.1), а конструкторная DI руками. Для публичного пакета
   `@nestjs/core` + `reflect-metadata` + `rxjs` + `class-validator` в hard-dependencies —
   стоп-сигнал. Связанность оказалась поверхностной: 14 `@Injectable`, 7 `@Module`,
   2 `@Inject`, `rxjs` ровно в одном HTTP-файле (`shutdown.interceptor.ts`).
3. **Целевой рантайм — веб-стандарты, а не Node.** `fetch`, `Request`/`Response`, WHATWG
   streams, Web Crypto, `FormData`/`Blob`. Это открывает Cloudflare Workers / Deno / Bun как
   площадки деплоя и заодно принудительно убирает вендорские SDK. Дисциплина проверяется
   в CI, иначе первый же `import { Readable } from 'node:stream'` тихо всё сломает.
4. **Ни ретраев, ни идемпотентности — нигде, включая HTTP-режим.** Rev. 1 оставляла
   HTTP-приложению in-memory идемпотентность «с задокументированной оговоркой про одну
   реплику». Оговорка выкинута вместе с механизмом: API, который делает вид, что дедуплицирует,
   хуже, чем API, который честно этого не делает.

Плюс одна новая проблема, которой в rev. 1 не было вовсе — **возобновляемые операции**
(Phase 2.6). Модель «ретраит вызывающий» ломается на многошаговых публикациях, и без хэндлов
она не просто неполна, а неверна.

Выкинуто из скоупа: n8n-нода (в репозитории её нет, пункт 8.6 rev. 1 описывал несуществующее).

## Разделение ответственности

| Забота | Владелец |
| --- | --- |
| Durable-состояние поста, дедуп уже опубликованного | Хост |
| Ретраи, backoff, dead-letter | Хост |
| Rate limiting между процессами | Хост |
| Хранение и шифрование токенов | Хост |
| OAuth authorization-code redirect (веб-флоу) | Хост |
| Перевод payload → вызовы платформенного API | **Пакет** |
| Хореография многошаговых публикаций | **Пакет** |
| Классификация ошибок (retryable / permanent / rate-limited + `retryAfterMs`) | **Пакет** |
| Возобновление прерванной многошаговой публикации | **Пакет** (состояние отдаётся хосту) |
| Capability-метаданные (лимиты, типы, форматы) | **Пакет** |
| Механика обновления OAuth-токена (не хранение) | **Пакет** |

Пакет «тонкий» по зависимостям и «толстый» по семантике. Пункты 2–4 в правой колонке — это не
довесок к «сделать HTTP-запрос»; без единой классификации ошибок хост физически не может
реализовать свои ретраи, ради которых всё и затевается.

## Целевая структура репозитория

```
packages/
  core/                  → @bozonx/social-posting            (0 рантайм-зависимостей)
  platform-telegram/     → @bozonx/social-posting-telegram
  platform-<network>/    → по одному пакету на сеть
apps/
  server/                → HTTP-шелл на Hono. НЕ публикуется в npm.
                           Артефакты: Docker-образ + Workers-деплой.
examples/
  embedded/              → минимальный in-process потребитель
  custom-platform/       → сеть, реализованная вне пакета
```

Правило зависимостей: `core` не знает ни про одну конкретную сеть; `platform-*` зависит только
от `core`; `apps/server` зависит от `core` + выбранных `platform-*`. Обратных рёбер нет.

## Текущее состояние — аудит

### Что уже работает и переносится как есть

- `IPlatform` / `PlatformRegistry` / `IAuthValidator` / `AuthValidatorRegistry` — реальный
  extension seam, никакого switch-case диспетчинга.
- Двойная точка входа уже существует: `src/main.ts` и `src/library.ts`.
- Path-алиасы внутри `src/` не используются — вывод `tsc` пригоден напрямую.
- ~5000 строк тестов: 20 unit-спеков и 4 e2e.
- Graceful shutdown, таймаут запроса с проброшенным `AbortSignal`, abort-aware sleep.
- `ILogger` / `ConsoleLogger` (`src/common/interfaces/logger.interface.ts`) — уже правильной
  формы, просто применяется неправильно (см. ниже).

### Блокеры встраивания

1. **Мутация глобального логгера Nest.** `createPostingClient` вызывает
   `NestLogger.overrideLogger(...)` (`src/library.ts`) — создание клиента перехватывает
   логирование всего процесса-хоста. `ILogger` при этом уже есть; его надо просто передавать
   конструктором, а не подменять им ambient-логгер Nest.
2. **Telegram зашит в фабрику.** `createPostingClient` инстанцирует `MediaService`,
   `TelegramTypeDetector`, `TelegramPlatform`, `TelegramAuthValidator` инлайном.
3. **Нет публичного контракта расширения.** `src/index.ts` не экспортирует `IPlatform`,
   `PlatformPublishResponse`, `IAuthValidator`, реестры; у `PostingClient` нет
   `registerPlatform()`.
4. **Мёртвая обвязка идемпотентности.** `new (IdempotencyService as any)(cacheManager, ...)`
   с полностью no-op кэшем. `@nestjs/cache-manager` + `cache-manager` оплачиваются впустую.
5. **Идемпотентность неверна by design.** `IdempotencyService` (267 строк) держит `Map`
   в памяти — при двух репликах дедупа нет. Конкурентные дубли возвращают `VALIDATION_ERROR`,
   что семантически неправильный код.
6. **Дублирование ретраев.** `PostService.publish` оборачивает `platform.publish` в
   `retryWithJitter(..., retryAttempts /* default 3 */)`. В стеке с ретраем HTTP-клиента хоста
   и BullMQ `attempts: 5` один пост даёт до 45 обращений к API платформы.
7. **Информация для ретрая не отдаётся.** `getErrorCode` определяет `RATE_LIMIT_ERROR`,
   но `retry_after` от платформы не читается и не возвращается (`grep retry_after` → пусто).
8. **Нетипизированные ошибки.** `post.service.ts` классифицирует через сниффинг `error: any`:
   строковые совпадения `'fetch failed'`, `'undici'`, чтение grammY-полей (`error.payload`,
   `error.description`) в *генерик*-слое. Телеграм протёк в ядро.
9. **Тяжёлая поверхность зависимостей.** `@nestjs/common`, `@nestjs/core`,
   `@nestjs/cache-manager`, `cache-manager`, `class-validator`, `class-transformer`, `rxjs`,
   `reflect-metadata` — всё это hard dependencies для потребителя библиотеки.
10. **Node-only рантайм.** Ничто сегодня не мешает Node-специфичному коду попасть в ядро.

### Пробелы расширяемости

11. **Только статические креды.** `auth: Record<string, string>` с синхронными строковыми
    валидаторами. X, LinkedIn, TikTok, YouTube, Meta/Threads, Pinterest, Reddit — все на OAuth2
    с истекающими токенами. Нет хука ни получить свежий токен, ни вернуть ротированный
    refresh-токен хосту. **Крупнейшая недостающая абстракция.**
12. **Нет примитивов загрузки.** `MediaService` — 45 строк, валидирующих строку URL.
13. **Нет модели отложенного результата.** `IPlatform.publish()` обязан вернуть финальный
    результат; TikTok и YouTube возвращают handle и материализуют пост минутами позже.
14. **Нет capability-дескриптора.** Лимиты ad-hoc: `supportedTypes` и `supportsCoverWithMedia`
    на интерфейсе, `MAX_MEDIA_GROUP_SIZE = 10` захардкожен внутри `TelegramPlatform`,
    `maxBody` в конфиге аккаунта.
15. **Preview-логика будет копипаститься.** `getRequiredFieldsErrors`,
    `getIgnoredFieldsWarnings`, `getIgnoredMediaWarnings` — ~150 рукописных строк внутри
    `TelegramPlatform` (файл на 650 строк). Написанное по разу на сеть, это станет главной
    статьёй стоимости добавления сети.
16. **Нет слоя рендеринга тела.** `bodyFormat` — свободная строка, каждая платформа трактует
    по-своему; целевые форматы (plain, HTML-подмножество, MarkdownV2), правила усечения и
    подсчёта длины URL различаются.
17. **`channelId` валидируется по-телеграмному.** `IsChannelId` кодирует `@name` / `-100…`
    в генерик-слое DTO.
18. **`scheduledAt` и `mode: 'publish' | 'draft'` — мёртвые поля.** Существуют в
    `PostRequestDto` и лишь сообщаются телеграмом как «проигнорированы».
19. **Автоопределение типа телеграм-специфично** (`TelegramTypeDetector`), генерика нет.

### Пробелы упаковки и CI

20. CI (`.github/workflows/docker-image.yml`) гоняет unit-тесты + `pnpm build` + сборку Docker.
    Нет lint, typecheck, e2e, **нет проверки `build:lib`**, нет публикации в npm.
21. В `package.json` нет `repository`, `bugs`, `homepage`, `publishConfig`, `sideEffects`,
    `prepack`. Публикация — ручной `pnpm lib:publish`.
22. `engines.node` говорит `>=24.0.0`, `AGENTS.md` говорит Node 22. CI берёт версию из
    `engines`, значит документация врёт.
23. Нет conformance-сьюта; `nock` присутствует только в `test/setup/unit.setup.ts` для блокировки
    сетевых коннектов, а не как механизм фикстур платформенных API.
24. `examples/test-platform-registration.ts` назван про внешнюю регистрацию, но прогоняет
    встроенную телеграм-обвязку.

## Политика зависимостей

**Ядро и platform-пакеты: ноль рантайм-зависимостей.** Вендорские SDK не берутся.

| Платформа | SDK, от которого отказываемся | Что вместо |
| --- | --- | --- |
| Telegram | `grammy` | Bot API — обычный HTTPS. Сейчас используется 6 вызовов (`sendMessage/Photo/Video/Audio/Document/MediaGroup`) плюс type-import `InputFile` |
| YouTube | `googleapis` (огромный, автогенерённый, Node-only) | Resumable upload: POST `…/upload/youtube/v3/videos?uploadType=resumable` → `Location` → PUT чанков с `Content-Range`. Refresh — POST на `oauth2.googleapis.com/token` |
| Meta (IG/FB/Threads) | `facebook-nodejs-business-sdk` | Graph API — plain REST: создать контейнер `POST /{ig-user-id}/media`, затем `POST /{ig-user-id}/media_publish` |
| TikTok | community-обёртки | `POST /v2/post/publish/video/init/` → `upload_url` + `publish_id` → PUT чанков → поллинг `/v2/post/publish/status/fetch/` |

Три причины, в порядке важности:

1. **SDK ломают контракт ошибок.** Они заворачивают ошибку в свой класс и теряют ровно то,
   ради чего существует Phase 2: исходный HTTP-статус, `retry_after`, платформенный код.
   Разворачивать обратно дороже, чем сразу читать ответ.
2. **SDK ломают веб-стандартный рантайм.** Почти все тянут Node-биндинги и не заводятся
   в Workers.
3. **SDK живут своим релизным циклом** и ломаются независимо от API. Продукт продаёт
   «актуальные рецепты запросов» — рецепт должен быть свой.

**Единственное допустимое исключение:** экзотическая криптография подписи запросов, которую
дороже реализовать, чем взять. Кандидат — Bluesky / AT Protocol (`@atproto/api`); решается
по факту, с обоснованием в PR. Исключение оформляется как `optionalDependencies` пакета
конкретной сети и никогда не попадает в `core`.

`apps/server` — отдельная история: там допустимы Hono и zod, потому что он не публикуется
в npm.

## План

Фазы упорядочены так, чтобы каждая была самостоятельно поставляемой и репозиторий не
оставался сломанным между ними.

### Phase 1 — Ядро без фреймворка

*Цель: `packages/core` собирается и проходит тесты, не имея ни одной рантайм-зависимости.*

- [x] **1.1 Развернуть monorepo.** Заполнить `packages` в `pnpm-workspace.yaml` (сейчас там
      только `allowBuilds` и `overrides`, декларации пакетов нет). Перенести `src/` в
      `packages/core/src`, телеграм — в `packages/platform-telegram`, `main.ts` +
      `app.module.ts` + контроллеры + guard + `config.yaml` + Docker — в `apps/server`.
- [x] **1.2 Убрать `NestLogger.overrideLogger`** из `library.ts`. `ILogger` уже существует
      и уже правильной формы — передавать его конструктором в каждый сервис.
- [x] **1.3 Снять Nest-декораторы с ядра.** Заменить `@Injectable` (14 шт.) и `@Module` (7 шт.)
      конструкторной DI. Композиционный корень — единственная фабрика `createPostingClient`.
      `rxjs` уходит вместе с `shutdown.interceptor.ts` в `apps/server`.
- [x] **1.4 Убрать `class-validator` / `class-transformer` из ядра.** Написать
      `validatePostRequest()` — простую структурную проверку без декораторов. Богатые
      per-platform правила приходят в Phase 4 из дескриптора; здесь нужен только минимум.
      DTO становятся плоскими интерфейсами. `reflect-metadata` уходит.
- [x] **1.5 Удалить `IdempotencyService`** (267 строк) и фейковый cache manager из
      `library.ts`. `@nestjs/cache-manager` и `cache-manager` — из зависимостей. Идемпотентность
      целиком переходит хосту; см. 2.5 про документацию.
- [x] **1.6 Ввести веб-стандартную дисциплину и закрепить её в CI.** Два уровня:
      - ESLint `no-restricted-imports` в `packages/**`: запрет `node:*`, `fs`, `path`, `stream`,
        `crypto`, `buffer`, `http`, `https`, `os`, `child_process` — быстрый барьер;
      - реальный прогон unit-тестов ядра под `workerd` (Miniflare /
        `@cloudflare/vitest-pool-workers`) — настоящая проверка.
      Оба обязательны: lint ловит опечатку, workerd ловит транзитивную зависимость.
- [x] **1.7 `apps/server` временно остаётся на Nest**, потребляя новое vanilla-ядро. Nest,
      обёрнутый вокруг обычных классов, работает без вопросов. Аргумент про зависимости уже
      выигран на этом шаге, потому что сервер не публикуется в npm. Замена на Hono — Phase 7.
- [x] **1.8 `examples/embedded/`** — минимальный in-process потребитель, публикующий
      замоканный пост и проверяющий, что глобальное состояние не тронуто и свой логгер
      не перехвачен. Завести в CI.

**Готово, когда:** `packages/core/package.json` имеет пустой `dependencies`, клиент
инстанцируется дважды в одном процессе с разными логгерами и разными аккаунтами, а тесты ядра
зелены под `workerd`.

### Phase 2 — Контракт результата

*Цель: всё, что `publish()` может вернуть кроме успеха, описано типами один раз.*

Rev. 1 разносила ошибки (Phase 2) и отложенные результаты (Phase 7) по разным концам плана.
Они объединены: и то и другое — ответ на вопрос «публикация не завершилась, что дальше»,
и проектировать это надо один раз, а не два.

- [x] **2.1 `retryAttempts` → 1 везде**, включая HTTP-режим. Ретраит вызывающий. Громко
      задокументировать в `docs/CHANGELOG.md` — поведенческое ломающее изменение.
- [x] **2.2 Типизированный `PlatformError`** (`packages/core/src/errors/platform-error.ts`):
      `code: ErrorCode`, `retryable: boolean`, `retryAfterMs?: number`, `httpStatus?: number`,
      `platformCode?: string`, `resumeHandle?: ResumeHandle`, `cause`. Платформы бросают его;
      ядро больше никогда не сниффит строки.
- [x] **2.3 Расширить `ErrorCode`.** К текущим семи (`VALIDATION_ERROR`, `TIMEOUT_ERROR`,
      `NETWORK_ERROR`, `RATE_LIMIT_ERROR`, `PLATFORM_ERROR`, `AUTH_ERROR`, `INTERNAL_ERROR`)
      добавить `CONTENT_REJECTED` (модерация/политика), `QUOTA_EXCEEDED` (суточная квота),
      `AUTH_REFRESH_REQUIRED` (нужна переавторизация канала — хост должен пометить канал,
      а не ретраить вечно).
- [x] **2.4 Перенести маппинг ошибок Telegram в `platform-telegram`.** Читать
      `parameters.retry_after` → `retryAfterMs`. Убрать `error.payload` / `error.description`
      и строковые совпадения `'fetch failed'` / `'undici'` из `post.service.ts`.
- [x] **2.5 Статус публикации.** Расширить исход до
      `{ status: 'published' | 'processing', postId, url?, checkAfterMs?, handle? }`
      и добавить опциональный `IPlatform.checkStatus(handle)` → published / processing / failed
      с причиной. Поллинга внутри пакета нет: пакет отдаёт проверку, хост ставит follow-up job.
- [x] **2.6 Возобновляемые операции — `ResumeHandle`.** ⚠️ Нового в rev. 1 не было.
      Публикация в большинстве сетей — 3–5 последовательных вызовов (Meta: контейнер →
      publish; X: INIT/APPEND/FINALIZE; LinkedIn: register → PUT → create; TikTok:
      init → upload → poll). Если падает третий шаг, наивный ретрай хоста стартует с первого
      и создаёт второй залитый файл, второй контейнер, дубль поста.
      Поэтому `PlatformError` несёт `resumeHandle` с уже достигнутым состоянием
      (`uploadId`, `containerId`, `publishId`, byte offset, номер шага), а
      `publish(request, { resume })` умеет продолжить с места падения. Хэндл обязан быть
      сериализуемым в JSON — хост кладёт его в свою job-запись.
      **Без этого модель «ретраит хост» не просто неполна, а неверна:** хост ничего не знает
      о промежуточных шагах и не может ретраить безопасно.
- [x] **2.7 Транспортный микроретрай — только он.** Одна повторная попытка при сбросе
      соединения *до* отправки первого байта тела безопасна; после завершения запроса — нет.
      Провести это различие явно в коде и в JSDoc.
- [x] **2.8 `docs/DELIVERY-SEMANTICS.md`** — окно риска дублей по каждой сети: у кого есть
      нативная идемпотентность, где возможна сверка через «список последних постов», а где
      at-least-once неустраним. Здесь же — что пакет не хранит ничего и почему.

**Готово, когда:** потребитель может удалить свою HTTP-обёртку ретраев и вести backoff
исключительно по `retryable` + `retryAfterMs`, а прерванную многошаговую публикацию —
продолжить, а не начать заново.

### Phase 3 — Публичный extension API

*Цель: сеть реализуется без единой правки в core.*

- [x] **3.1 Экспортировать контракт** из `packages/core`: `IPlatform`,
      `PlatformPublishResponse`, `IAuthValidator`, `PlatformCapabilities`, `PlatformError`,
      `ErrorCode`, `ResumeHandle`, `MediaSource`, базовые хелперы.
- [x] **3.2 Дескрипторы `PlatformModule`.** Каждая сеть экспортирует один объект-фабрику:
      ```ts
      export const telegram: PlatformModule = {
        name: 'telegram',
        capabilities: telegramCapabilities,
        create: (deps) => new TelegramPlatform(deps),
        authValidator: new TelegramAuthValidator(),
      };
      ```

### Phase 6 — Media pipeline

*Цель: поддержать сети, требующие настоящей загрузки байтов.*

- [x] **6.1 `MediaSource`** — URL, `Blob`/`Uint8Array` или фабрика WHATWG `ReadableStream`,
      заменяющая на внутренней границе `MediaInput.src`, который сегодня только строка-URL.
      Публичный DTO остаётся обратно совместимым. **Node-`Readable` не использовать** — это
      прямое нарушение 1.6.
- [x] **6.2 URL-passthrough как первоклассный быстрый путь.** Это не телеграм-частность:
      Meta Graph API принимает `image_url` / `video_url` и качает сам, TikTok умеет
      `PULL_FROM_URL` (требует верификации домена). Для сетей с
      `supportsUrlPassthrough` байты вообще не проходят через процесс — именно это делает
      Workers-деплой пригодным, а не декоративным.
- [x] **6.3 `MediaFetcher`**: стримит удалённый источник, определяет content-length и mime
      (из заголовков, с откатом на сигнатуру первых байт, а не на расширение в URL),
      проверяет лимиты дескриптора **до** начала загрузки, уважает `AbortSignal`.
- [x] **6.4 `ChunkedUploader`**: переиспользуемый драйвер формы INIT/APPEND/FINALIZE с
      настраиваемым размером чанка, per-chunk ретраем и **resume-from-offset, выдающим
      `ResumeHandle` из 2.6**. Общий субстрат для X, TikTok, YouTube и LinkedIn.
- [x] **6.5 Никогда не буферизовать файл целиком.** Тест: заливка большого синтетического
      потока с проверкой, что пиковая память ограничена. Критично и для воркеров хоста,
      гоняющих задачи параллельно, и для лимита памяти изолята в Workers.

**Готово, когда:** сеть с трёхшаговой чанковой загрузкой не требует новой HTTP-обвязки.

### Phase 7 — HTTP-шелл на Hono

*Цель: один и тот же шелл едет и в Docker, и в Workers.*

- [x] **7.3 Два артефакта деплоя:** Docker-образ (Node) и Workers (`wrangler`). Оба собираются

## Definition of done

Добавление сети состоит ровно из этого, без правок в core:

```
packages/platform-<network>/
  src/capabilities.ts    # данные: лимиты, типы, форматы, квоты, транспортные признаки
  src/platform.ts        # publish() (+ checkStatus(), + resume, если многошаговая), маппинг ошибок
  src/auth.validator.ts  # валидация формы кредов
  src/index.ts           # дескриптор PlatformModule
  test/fixtures/…        # записанные ответы API: успех и отказы
  test/platform.spec.ts  # contract-сьют + специфика
```

плюс строка в README-таблице поддержки.

## Порядок работ

- **Фазы 1–2 — блокеры интеграции.** Делать первыми: после них потребитель переключается
  на in-process драйвер, всё ещё поддерживая только телеграм.
- **Phase 3** следом — дёшево и останавливает нарастание хардкода в фабрике.
- **Фазы 4–6 — основная инвестиция.** Не начинать вторую сеть до появления Phase 5 (OAuth)
  и Phase 6 (загрузки): иначе их отсутствие обойдут внутри платформы, и обход станет
  шаблоном для всех последующих сетей.
- **Phase 7** можно двигать раньше, если Workers-деплой нужен скорее; он зависит только
  от Phase 1. По умолчанию — здесь, чтобы не переписывать шелл дважды.
- **Фазы 8–9** приземлять вместе с Phase 3: публикация и conformance — то, что делает seam
  настоящим, а не номинальным.

## Порядок сетей

По количеству новой инфраструктуры, которую каждая заставляет построить:

1. **VK** — статический токен, но прогоняет многошаговую загрузку (Phase 6) без OAuth.
2. **Mastodon / Bluesky** — небольшие, хорошо документированные API; вторая проверка
   capability-модели. У Bluesky отдельно решить вопрос `@atproto/api` по политике исключений.
3. **LinkedIn** — первая OAuth-сеть; прогоняет Phase 5 целиком.
4. **X** — чанковая загрузка плюс строгие правила подсчёта символов.
5. **Meta (Instagram / Facebook / Threads)** — контейнерная публикация, обмен на долгоживущий
   токен; Graph REST напрямую.
6. **TikTok / YouTube** — отложенные результаты и модерация; требуют 2.5.
