# План доработки ядра и подготовки к добавлению платформ

Дата составления: 29 августа 2026 года.
Родительский документ: [PLAN-PLATFORMS-RU.md](./PLAN-PLATFORMS-RU.md) — состав набора сетей,
матрица типов, платформенные планы и границы сервиса.

Этот документ — **инженерный план работ по `packages/core`** (плюс `conformance`,
`platform-catalog`, `platform-telegram`, `apps/server`). Он переводит пункты 1–23 родительского
плана в последовательность задач с конкретными файлами, сигнатурами и критериями приёмки.

## Принцип, который определяет весь порядок работ

Все изменения ниже — **изменения публичных типов**. Пока в репозитории один адаптер
(`platform-telegram`) и один потребитель (`../bloggerdog`), каждое из них стоит один рефакторинг.
После пятнадцати адаптеров — пятнадцать. Поэтому:

> **Ни один новый адаптер не начинается, пока не закрыты этапы 1–5 и не пройдена
> бумажная контрольная точка (этап 7).**

**Обратная совместимость со старым API не сохраняется — это осознанное решение, а не риск.**
Библиотека дорабатывается до правильной формы типов, после чего потребитель (`../bloggerdog`)
переписывается под неё. Отсюда прямые следствия, действующие на всех этапах:

- никаких алиасов старых имён, никаких deprecated-полей, никаких «пока принимаем и то, и то»;
- никаких фолбэков и мягких деградаций: неподдерживаемая форма запроса — ошибка, а не
  молчаливое приведение к ближайшей поддержанной;
- никаких слоёв совместимости и адаптеров старого контракта внутри ядра;
- ломающие изменения не растягиваются на несколько релизов — они выходят одним куском.

Ломать BloggerDog на этом этапе допустимо и ожидаемо. Порядок работ: сначала ядро и
`platform-telegram` приводятся к целевому виду, затем потребитель переписывается на новый
контракт (этап 8, пункт 5). Обратный порядок — попытка не ломать потребителя — и есть то, что
порождает legacy.

Второе правило, действующее на всех этапах: ядро остаётся stateless, без runtime-зависимостей и
без Node built-ins — только Web APIs (`fetch`, `Request`/`Response`, WHATWG streams, Web Crypto).
Всё, что является состоянием (кэш capabilities, resume handle, токены, client credentials
инстанса), библиотека **возвращает хосту**, а не хранит.

## Этап 1. Словарь типов постов

**Цель:** один источник истины по именам типов, чтобы через десять сетей не оказалось
`shortVideo` и `short_video` одновременно.

Файлы: `src/types/post-type.ts`, `src/validation/detect-post-type.ts`,
`src/validation/capability-validator.ts`.

1. Добавить в `PostType` явный `SHORT_VIDEO: 'shortVideo'`. Алиасов и обратной совместимости со
   старым способом («вертикальное видео») не вводить.
2. Зарезервировать канонические имена под будущее, не реализуя их поведение:
   `story` (уже есть), `thread`, `event`, `live`. `article` уже есть.
3. Экспортировать `CANONICAL_POST_TYPES: readonly string[]` и предикат
   `isCanonicalPostType(name)`.
4. `validateCapabilities()` требует: каждый ключ `capabilities.postTypes` либо каноничен, либо
   начинается с префикса платформенного расширения (`x-<platform>-…`). Иначе — `ValidationError`
   на этапе регистрации модуля, а не при публикации.
5. `detectPostType()` **не** выводит `shortVideo` и `story` сам: они приходят только явно. Для
   `auto` сохраняется вывод `post`/`image`/`album`/`video`/`audio`/`document`.

**Приёмка:** conformance-набор содержит кейс «регистрация модуля с типом `short_video` падает»;
`detectPostType()` ни при каких медиа не возвращает `shortVideo`.

## Этап 2. Медиа: набор вложений, видео-правила и транспорт

**Цель:** разделить «какой это пост» и «что в нём лежит», и объявлять, кто тянет байты.

Файлы: `src/platforms/capabilities.ts`, `src/validation/validate-post-request.ts`,
`src/validation/detect-post-type.ts`, `src/types/media-input.ts`.

1. **Набор вложений.** `ALBUM` перестаёт означать «два и более медиа». Валидация опирается на
   `mediaCounts` и `allowsMixedMedia` (поля уже есть) плюс новый хук `validateExtra` адаптера.
   Для каждого типа проверяются: общее число, число по видам, смешение видов — до первого
   HTTP-запроса.
2. **Видео-ограничения.** Дополнить `MediaConstraints`:
   ```ts
   minFrameRate?: number;
   maxFrameRate?: number;
   containers?: string[];        // 'mp4', 'mov', 'webm'
   videoCodecs?: string[];       // 'h264', 'hevc', 'vp9'
   audioCodecs?: string[];
   requiresCover?: boolean;      // обязательная обложка (Pinterest, TikTok photo)
   ```
   Ограничения на aspect ratio и размеры уже есть; проверять их одинаково для всех сетей.
   Значения, которые нельзя вычислить без разбора файла (кодек, fps, длительность), — это
   декларация для хоста и для `preview()`, а не гарантия ядра: ядро проверяет их, только если
   `MediaInput` их несёт.
3. **Транспорт.** Дополнить `MediaConstraints`:
   ```ts
   transport: 'push' | 'pull' | 'both';
   requiresPubliclyFetchableUrl?: boolean;
   urlMustRemainAvailableForSecs?: number;
   ```
   Валидация: если единственный переданный источник — `url`, а `transport === 'push'` и сеть не
   умеет тянуть — отказ до запроса. Если `transport` включает `pull`, `preview()` возвращает
   `urlMustRemainAvailableForSecs` в результате, чтобы хост знал требуемый срок жизни подписанной
   ссылки.

**Приёмка:** телеграм-дескриптор переписан на новые поля без изменения поведения; conformance
проверяет отказ «pull-сеть получила `bytes`» и «push-сеть получила только `url`».

## Этап 3. Адресация: `target`, `apiBaseUrl`, типизированный `extra`

**Цель:** одна публикация должна быть адресуема в сети с составным адресом и на чужом хосте.

Файлы: `src/types/post-request.ts`, `src/types/account-config.ts`,
`src/types/post-response.ts`, `src/platforms/capabilities.ts`, `src/config/posting-config.ts`.

1. **Структурный target.**
   ```ts
   export interface PlatformTarget {
     id: string;
     [key: string]: unknown; // поля описаны в capabilities.targetSchema
   }
   export type TargetInput = string | number | PlatformTarget;
   ```
   `PostRequest.target`, `AccountConfig.target`, `PostRef.target` и `PlatformObjectRef.target`
   принимают `TargetInput`. Скаляр — не «совместимость со старым API», а сокращение для сетей с
   единственным идентификатором; ядро нормализует его в `{ id: String(value) }`, и адаптер видит
   **только** нормализованную форму. Если после проработки окажется, что сокращение не нужно, —
   убрать его и оставить один `PlatformTarget`, не сохраняя скаляр ради старых вызовов.
   В capabilities добавляется `targetSchema?: ExtraFieldSpec[]` — тот же механизм, что для
   `extra`, с той же рантайм-валидацией.
2. **`apiBaseUrl`.** В `AccountConfig` — `apiBaseUrl?: string`; в capabilities —
   `requiresApiBaseUrl?: boolean`. Ядро валидирует наличие и то, что это абсолютный https-URL.
   Адаптер получает базовый URL из аккаунта, а не из константы пакета. Для сетей с одним хостом
   поле опционально и адаптер подставляет свой дефолт.
3. **Дженерик `extra`.** `PostRequest<TExtra = Record<string, unknown>>` с
   `extra?: TExtra`. Каждый пакет платформы экспортирует свой интерфейс (`TelegramExtra`, …).
   Рантайм-валидация по `ExtraFieldSpec[]` остаётся единственным источником истины; дженерик —
   удобство компиляции для хоста. Значение по умолчанию нужно для эргономики (`PostRequest` без
   параметра остаётся осмысленным), а не для совместимости.

**Приёмка:** `platform-telegram` переведён на нормализованный target; в conformance есть кейс
сети с двухчастным target (фикстура «board + section»); плоский `request.extra` без неймспейса
у потребителя больше не является поддержанной формой.

## Этап 4. Динамические возможности и квоты

**Цель:** `preview()` должен быть достоверным для сетей, чьи лимиты известны только в рантайме.

Файлы: `src/platforms/platform.interface.ts`, `src/platforms/capabilities.ts`,
`src/services/preview.service.ts`.

1. Новый необязательный член `IPlatform`:
   ```ts
   resolveCapabilities?(
     accountConfig: ResolvedAccountConfig,
     signal?: AbortSignal,
   ): Promise<ResolvedCapabilities>;

   interface ResolvedCapabilities {
     capabilities: PlatformCapabilities;   // merge статики и рантайма
     cacheableForSecs?: number;            // 0 — «получать всегда»
     fetchedAt: string;                    // ISO-8601
   }
   ```
2. **Библиотека не кэширует.** Результат возвращается хосту вместе с `cacheableForSecs`; решение
   о Redis/БД принимает хост. В `docs/` фиксируется правило: `cacheableForSecs: 0` (TikTok
   Creator Info) означает обязательный вызов перед каждой публикацией.
3. Merge-семантика описывается явно и реализуется в ядре, а не в каждом адаптере: рантайм-поля
   **переопределяют** статические скаляры, списки заменяются целиком, отсутствующие в рантайме
   поля берутся из статики.
4. `preview()` и валидация используют разрешённые capabilities, если адаптер их предоставил и
   хост передал полученный объект; иначе — статические.
5. **Квоты.** `RateLimits` дополняется:
   ```ts
   quotaCost?: { unit: string; perPublish?: number };   // YouTube: 'quotaUnits'
   quotaKind?: 'operations' | 'storage' | 'rollingWindow';
   ```
   и необязательный `getQuota?(accountConfig, signal): Promise<QuotaState>` в `IPlatform` — для
   сетей с официальным endpoint остатка (Vimeo — хранилище, Instagram — скользящее окно).

**Приёмка:** в conformance есть фиктивная платформа с `resolveCapabilities()`, и тест
доказывает, что ядро не запоминает результат между вызовами.

## Этап 5. Асинхронность, возобновление, загрузка, большие потоки

**Цель:** ни одна неопределённость в сети не должна приводить к дублю публикации.

Файлы: `src/types/resume-handle.ts`, `src/media/chunked-uploader.ts`, `src/http/http-request.ts`,
новый `src/media/multipart.ts`, `apps/server`.

1. **Handle — только JSON-состояние.** В `ResumeHandle` запрещены access token, подписанный
   upload URL и любые заголовки авторизации. Вводится проверка при сериализации (в dev/тестах —
   бросает, в проде — вырезает и логирует предупреждение). Handle обязан быть достаточным для
   `checkStatus()` после рестарта процесса.
2. **Retry не универсален.** В ядре фиксируется:
   - безопасно повторять: адресованный chunk по offset, `status`-вызов, `init` до получения id;
   - **небезопасно** повторять: `create`/`publish` после неопределённого ответа (таймаут, 5xx
     без тела). Вместо повтора — платформенный `reconcile?(handle, accountConfig, signal)`,
     который выясняет, создалась ли публикация. Сети без такой возможности объявляют
     `supportsIdempotencyKey` и обязаны получать `idempotencyKey`; если ни того, ни другого нет,
     ядро возвращает `UNKNOWN_OUTCOME` вместо повтора.
   - в `ErrorCode` добавляется `UNKNOWN_OUTCOME` — исход, который хост обязан показать иначе,
     чем ошибку.
3. **Upload helpers.** Рядом с существующим `runChunkedUpload()` (offset-протоколы) добавить:
   `buildMultipartFormData()` на Web APIs (`FormData` + `Blob`, без Node `form-data`),
   `runSinglePartUpload()` и общий каркас `init → upload → finalize → status` с раздельными
   шагами в handle.
4. **Большие потоки.** HTTP shell в `apps/server` не принимает видео в JSON/base64. Допустимые
   пути: (а) `url`-источник, который тянет адаптер или сеть; (б) отдельный streaming ingress с
   `Content-Type: application/octet-stream` и передачей `ReadableStream` в адаптер без
   материализации в памяти. Общий body limit остаётся для JSON-эндпоинта.

**Приёмка:** workerd-тест грузит файл больше лимита памяти воркера потоком; тест на
«неопределённый ответ create» возвращает `UNKNOWN_OUTCOME`, а не второй пост.

## Этап 6. Расширяемость модели: auth, статьи, треды, preview, диалекты

**Цель:** зарезервировать формы, которые потом менять дорого. Реализация поведения — по мере
появления сетей; типы вводятся сейчас.

Файлы: `src/auth/oauth2.ts`, `src/auth/credentials.ts`, `src/platforms/platform-module.ts`,
`src/platforms/platform.interface.ts`, `src/types/preview-response.ts`,
новый `src/types/article-document.ts`.

1. **OAuth per-instance.** `OAuth2Config` строится функцией `(account) => OAuth2Config`, а не
   константой пакета: у Mastodon/Pixelfed `clientId`/`clientSecret` свои на каждом инстансе.
   `CredentialProvider` для таких аккаунтов хранит client credentials наравне с токенами; хост
   обязан их персистить. Библиотека даёт helper для формирования запроса регистрации приложения
   (`POST /api/v1/apps`), но сам redirect-flow остаётся у хоста.
   Отдельно: `IPlatform` **не должен** требовать OAuth2 как единственный путь — ATProto
   (app password + сессия) обновляется своим механизмом. Сейчас это свойство есть; при
   рефакторинге сохранить его осознанно и закрыть тестом.
2. **`ArticleDocument`.** Отдельный тип: обязательный `title` и упорядоченные блоки
   (`paragraph`, `heading`, `list`, `quote`, `code`, `image`) с необходимым набором inline-marks.
   `PostType.ARTICLE` требует этот документ; capability перечисляет допустимые blocks/marks и
   отказывает в неподдерживаемых. Ни один адаптер набора статьи не объявляет — тип вводится
   пустым, но с валидацией.
3. **Треды.** `thread?: PostSegment[]` в `PostRequest` (`body`, `media`, `poll` на сегмент) и
   `thread: { supported, maxSegments, maxSegmentBodyLength }` в capabilities. Результат —
   существующие `parts[]`, сбой в середине — существующий `ResumeHandle`. Автонарезка длинного
   текста не делается никогда: это решение вызывающего.
4. **`adaptedRequest` в preview.** `PreviewResult` дополняется полностью адаптированным
   запросом. Это снимает с хоста необходимость держать свои форматтеры на каждую сеть
   (у BloggerDog это `utils/strategies/`). Правило: `adaptedRequest` — детерминированная чистая
   функция от `(request, capabilities)`; сетевых вызовов в ней нет.
5. **Заглушка `edit()`.** Объявить необязательный
   `edit?(ref, request, accountConfig, options)` в `IPlatform` без реализаций — чтобы не менять
   форму `PostRef`, когда в БД хоста уже лежат миллионы ссылок.
6. **Диалекты API.** `PlatformModule` получает `dialect?: string` (`'mastodon-api'`, `'atproto'`),
   а ядро — `deriveModule(base, { name, capabilities })`. Один пакет отдаёт несколько сетей с
   разными дескрипторами вместо копий кода. Реестр платформ индексируется по `name`, а
   `dialect` — метаданные для документации и для выбора общих фикстур в conformance.

**Приёмка:** `deriveModule()` покрыт тестом на фиктивном базовом модуле; `PostRequest` с
`thread` и `ArticleDocument` валидируется, но отклоняется всеми существующими дескрипторами как
`unsupported` — молчаливой деградации нет.

## Этап 7. Контрольная точка на бумаге (блокирующая)

До первого нового адаптера описать **на бумаге** Mastodon и Bluesky против получившегося ядра и
убедиться, что обе ложатся без новых понятий:

- свой хост инстанса (`apiBaseUrl`);
- динамические лимиты из `/api/v1/instance` (`resolveCapabilities`);
- треды (`thread` + `parts`);
- `Idempotency-Key`;
- alt text;
- чужая единица счёта текста (графемы у Bluesky, UTF-8 байты в `facets`);
- не-OAuth2 аутентификация (ATProto).

Если хоть одна не ложится — ядро не готово, и это дешевле узнать здесь, чем на восьмом адаптере.
Результат проверки дописывается в этот файл отдельным разделом.

## Этап 8. Обвязка: каталог, конформанс, сервер, документация

1. **Каталог.** Убрать неподтверждённые значения (generic media sources у Facebook/Pinterest,
   YouTube MIME как только `application/octet-stream`, TikTok `ALBUM` из одного элемента,
   отсутствие различия Reel/Story/video). У каждого значения — официальный источник и
   `verifiedAt`. Каталог остаётся справкой, а не обещанием реализации.
2. **Conformance.** Расширить набор кейсами всех новых механизмов: канонические имена типов,
   транспорт медиа, структурный target, `resolveCapabilities`, `UNKNOWN_OUTCOME`, `deriveModule`.
   Правило: новый механизм ядра без conformance-кейса не считается сделанным.
3. **Сервер.** Streaming ingress, регистрация массива модулей (уже есть), `.env.example`,
   `config.yaml`.
4. **Документация.** `docs/PLATFORM-SPECIFICS.md`, OAuth-раздел, `docs/CHANGELOG.md`,
   `CONTRIBUTING-PLATFORMS.md` (сценарий «как добавить сеть» после всех изменений),
   `examples/`.
5. **Потребитель.** Переписать `../bloggerdog` под новый контракт — не адаптировать ядро под
   существующий код потребителя. Объём: `CredentialProvider` поверх БД с
   `onCredentialsRefreshed`, отображение prisma `PostType` → библиотечный тип, составной target,
   срок жизни подписанных media-URL, окно ожидания обработки на сеть. Без этого половина набора
   не заработает у единственного потребителя.

## Ломающие изменения: список, а не план миграции

Совместимость не поддерживается, поэтому здесь нет колонки «смягчение» — есть перечень того, что
меняется, чтобы это попало в `docs/CHANGELOG.md` и в задачу на переписывание потребителя.

| Изменение                                | Что перестаёт работать                                       |
| ---------------------------------------- | ------------------------------------------------------------ |
| `PostType.SHORT_VIDEO` и реестр имён      | произвольные строки в `postTypes` — ошибка при регистрации   |
| `TargetInput` вместо `string \| number`   | код, читающий `target` как скаляр внутри адаптера            |
| `apiBaseUrl` в `AccountConfig`            | базовый URL, зашитый в пакет платформы                        |
| `PostRequest<TExtra>` и неймспейс `extra` | плоский `extra` с ключами разных сетей                        |
| `transport` в `MediaConstraints`          | все существующие дескрипторы платформ (поле обязательное)     |
| `UNKNOWN_OUTCOME` в `ErrorCode`           | исчерпывающие `switch` по кодам ошибок у хоста                |
| `ResumeHandle` без секретов               | сохранённые старые handle — считаются невалидными            |
| `ArticleDocument` для `PostType.ARTICLE`  | `ARTICLE` с одним `body` и `media[]`                          |
| `adaptedRequest` в preview                | собственные форматтеры хоста (`utils/strategies/`)            |

Правило при выполнении любого этапа: если возникает соблазн оставить старый путь «на время» —
не оставлять. Старый путь удаляется в том же изменении, что вводит новый.

Порядок выполнения строго по этапам: 1 → 2 → 3 → 4 → 5 → 6 → **7 (блокирующая проверка)** → 8.
Этапы 1–3 можно вести параллельно разными изменениями, но релизить одним куском: они все
затрагивают `capabilities.ts` и дескриптор Telegram.

## Что делается параллельно и не ускоряется кодом

Подача заявок на доступ к TikTok, X и LinkedIn и запрос подтверждения условий по Truth Social
начинаются **вместе с этапом 1**, а не после ядра: сроки там измеряются неделями. Учётные записи
для smoke tests — блокирующее требование выпуска, а не пожелание.

## Готовность ядра к добавлению сетей — чеклист

Ядро считается подготовленным, когда все пункты верны одновременно:

- [ ] типы постов каноничны, `shortVideo` явный, нестандартное имя падает при регистрации;
- [ ] набор вложений валидируется отдельно от типа поста, до первого HTTP-запроса;
- [ ] видео-ограничения и транспорт медиа объявлены данными, а не проверяются кодом адаптера;
- [ ] target структурный и нормализованный; `apiBaseUrl` — свойство аккаунта;
- [ ] `resolveCapabilities()` есть, ядро его не кэширует, `preview()` его учитывает;
- [ ] `ResumeHandle` не содержит секретов и переживает рестарт процесса;
- [ ] неопределённый ответ `create` не приводит к повтору: есть `reconcile`/idempotency/`UNKNOWN_OUTCOME`;
- [ ] есть multipart и single-part helpers на Web APIs;
- [ ] большое видео проходит через сервер потоком, а не через JSON;
- [ ] OAuth-конфигурация строится из аккаунта; не-OAuth2 путь возможен;
- [ ] `thread`, `ArticleDocument`, `edit()`, `adaptedRequest` объявлены;
- [ ] `deriveModule()` работает и покрыт тестом;
- [ ] `platform-telegram` переведён на всё вышеперечисленное; старые пути в нём удалены, а не
      оставлены рядом;
- [ ] в ядре нет алиасов, deprecated-полей и веток совместимости со старым контрактом;
- [ ] conformance покрывает каждый новый механизм;
- [ ] `pnpm validate` и `pnpm validate:all` проходят;
- [ ] бумажная проверка Mastodon и Bluesky (этап 7) пройдена и записана.

## Явно вне этого плана

Редактирование, удаление в новых адаптерах, аналитика, чтение лент, комментарии, модерация,
собственный планировщик, автонарезка длинного текста на несколько постов.

публикации обновлений канала не существует. Обоснование —
